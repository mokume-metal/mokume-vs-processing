# 0001 — 何を揃えれば公正な比較と言えるか

## 状態

採用 (2026-09-25)

## 文脈

このリポジトリは「Processing とほぼ同じ内容を mokume で書くと、速く、書き方も良い」ことを
**事例で示す**ためにある。読み手は外の人で、数字は mokume を選ぶ根拠として読まれる。

だから一番の危険は、**比べ方が mokume に有利に偏っていて、それが後から見抜かれること**である。
1 件でも見抜かれれば、他の事例の数字まで信用されなくなる。何を揃えたかを先に決めて明文にしておく。

mokume には比べ方を縛る性質が 2 つある (mokume v0.11.2 で確認):

- **窓に出す経路では fps の上限を外せない。** 表示の同期 (`CADisplayLink`) に `frameRate` を
  固定しており、「上限なしで何 fps 出るか」は測れない
- `draw()` の中は図形を溜めるだけで、符号化と GPU への投入はその後に走る。**`draw()` の所要時間
  では仕事の全体が見えない**

## 決定

### 1. 目標 60 fps で負荷を上げ、どこまで保てるかで比べる

両側とも `frameRate` を 60 にし、負荷 (粒子の数など) を段階的に上げて、各段の実効 fps と
フレーム間隔の p95 を取る。「上限なしの fps」は mokume が測れないので比べない。
作品を作る人にとって意味があるのも「60 fps を保てる規模」のほうである。

### 2. 測るのは draw の開始どうしの間隔。統計はハーネスが取る

両側のスケッチは、同じ取り決め (harness/README.md) で `draw()` の頭の時刻を記録し、間隔を
生のまま書き出す。平均・分位・fps はハーネスが両側に同じ式で掛ける。fps は間隔の平均の逆数とする
(フレームごとの fps の平均は遅いフレームを軽く数える)。

### 3. 揃える条件

| 条件 | 値 |
| --- | --- |
| 大きさ | 1280 × 720、pixelDensity 1 |
| 窓の大きさ | 1280 × 720 **点** (描く大きさと同じ数の点)。Retina では両側とも 2 倍に拡大して出す |
| Processing の描き方 | **P2D** (GPU)。既定の JAVA2D は CPU で描くので相手として弱すぎる |
| mokume の組み方 | release (`swift build -c release`)。debug の数字は使わない |
| 捨てる時間 | 最初の 2 秒 (JIT の暖機・資源の確保) |
| 測る時間 | 5 秒 |
| 窓 | 両側とも窓を出し、前面に置く。背面では描画の頻度が落ちる |
| 同じ機械で続けて測る | 結果には機械・macOS・両側の版を刻む |

### 4. 同じ書き方の事例と、らしい書き方の事例を分ける

1 つの事例の中で両側のコードは**同じ書き方**に揃える (特定の API の速さではなく、同じコードを
書いたときの差を見る)。mokume にしかない書き方で速くなるものは、**別の事例**として足し、
「同じ書き方の事例」と並べて見せる。混ぜると、差が道具の差なのか書き方の差なのか言えなくなる。

### 5. 生の記録はコミットしない

`results/` は gitignore する。事例の README に載せるのは要約の表と、それを測った条件
(harness の出す最後の 1 行) だけにする。

窓の大きさを揃えるのは、見た目のためだけではない。**窓が違えば画面へ出す画素の数が違い、
出力段の仕事量が片側だけ変わる。** Processing の `size(1280, 720)` は窓を 1280 × 720 点で開くが、
mokume (0.11.2) は描く解像度の半分の点で開き、大きさを選ぶ口が無い
([mokume#1624](https://github.com/mokume-metal/mokume/issues/1624))。それまでは mokume 側の
`Recorder` が最初のフレーム (暖機の中) で窓を広げて揃える。描く解像度には触れない。

## 影響

- 数字の見出しは「60 fps を保てる最大の負荷」になる。上限なしの fps を期待する読み手には、
  README で理由を示す
- 窓を出す計測なので CI では回らない。計測は手元で行い、表を貼る PR に条件の 1 行を必ず添える
- mokume が上限なしの経路を持ったら、決定 1 を見直す
